# ტურის დაჯავშნა, გადახდა და მფლობელის შეტყობინება

ეს არის Visual Studio Code-ში გასახსნელი, გასაშვები საწყისი პროექტი. ძირითადი ლოგიკა დაწერილია **TypeScript + Node.js**-ზე; ინტერფეისი არის HTML, CSS და JavaScript. ნაგულისხმევად ყველაფერი მუშაობს ადგილობრივ საცდელ რეჟიმში: **ბანკთან მოთხოვნა არ იგზავნება, თანხა არ ჩამოიჭრება და რეალური ელფოსტა არ იგზავნება.**

პროექტს აქვს TBC E-Commerce-ის API-ისთვის დაწერილი ინტეგრაციაც. მისი რეალურ ბანკთან მუშაობა უნდა გადაამოწმოთ თქვენი მერჩანტის მონაცემებით და ბანკთან შეთანხმებული ტესტით. კოდის არსებობა არ ნიშნავს, რომ საბანკო მომსახურება უკვე გააქტიურებულია.

## 1. გაშვება Visual Studio Code-ში

1. დააყენეთ [Node.js 24 LTS](https://nodejs.org/en/download). გამოიყენეთ 24.x ხაზის განახლებული ვერსია. პროექტი შემოწმებულია Node.js 24.22.1-ზე.
2. გაშალეთ ZIP. Visual Studio Code-ში აირჩიეთ **File → Open Folder** და გახსენით `tour-booking` საქაღალდე, სადაც `package.json` არის.
3. გახსენით **Terminal → New Terminal**. გაუშვით:

```powershell
npm ci
Copy-Item .env.example .env
npm run dev
```

macOS/Linux-ზე მეორე ბრძანება იქნება `cp .env.example .env`. `.env` დააკოპირეთ მხოლოდ პირველად, რათა შემდეგ თქვენი პარამეტრები არ გადაიწეროს.

4. ბრაუზერში გახსენით **http://localhost:3000**.

სერვერი მუშაობს, სანამ ტერმინალი გაშვებულია. შეჩერება: `Ctrl+C`. ცვლილებების შემდეგ განვითარების რეჟიმი სერვერს ავტომატურად გადატვირთავს. გვერდი განაახლეთ ბრაუზერშიც. VS Code-ის Debug ჩანართში არის `Tour booking (TypeScript)` კონფიგურაციაც.

თუ PowerShell წერს, რომ `npm.ps1` ვერ გაეშვება, გამოიყენეთ `npm.cmd ci` და `npm.cmd run dev`, ან VS Code-ში აირჩიეთ Command Prompt ტერმინალი. სისტემის დაცვის გამორთვა საჭირო არ არის.

თუ პორტი 3000 დაკავებულია, `.env`-ში შეცვალეთ `PORT=3001` და `APP_URL=http://localhost:3001`, შემდეგ თავიდან გაუშვით სერვერი.

## 2. რა უნდა სცადოთ

1. აირჩიეთ ერთ-ერთი ნიმუშის ტური: ყაზბეგი, კახეთი ან მცხეთა.
2. მიუთითეთ თარიღი, მგზავრების რაოდენობა, სახელი, ტელეფონი და ელფოსტა.
3. დააჭირეთ **საცდელი გადახდა**.
4. აირჩიეთ **წარმატებული გადახდის ცდა**.
5. გამოჩნდება დადასტურებული საცდელი ჯავშანი და **მფლობელის შეტყობინების ნახვა**.
6. ახალი ჯავშნით სცადეთ წარუმატებელი შედეგიც: ამ შემთხვევაში დადასტურების წერილი არ შეიქმნება.

საცდელი ფასებია: ყაზბეგი 120 GEL, კახეთი 95 GEL, მცხეთა 65 GEL ერთ ადამიანზე. ისინი რეალურ შეთავაზებას არ წარმოადგენს. ყველა ტურითა და თარიღით მუშაობს მარტივი მაგალითი; ხელმისაწვდომი ადგილების კალენდარი ამ ვერსიაში არ არის.

## 3. როგორ მუშაობს რეალური გადახდის პროცესი

1. მომხმარებელი ავსებს ფორმას.
2. სერვერი ამოწმებს მონაცემებს, თავად ითვლის ფასს და ჯავშანს ბაზაში ინახავს.
3. სერვერი TBC-ს სთხოვს გადახდის შექმნას და ინახავს ბანკის დაბრუნებულ `payId`-ს.
4. მომხმარებელი გადადის ბანკის დაბრუნებულ გადახდის გვერდზე და ბარათის მონაცემებს იქ წერს.
5. ბანკი სერვერის `callback` მისამართზე გზავნის `PaymentId`-ს.
6. სერვერი საკუთარი საბანკო ავტორიზაციით ხელახლა კითხულობს გადახდის დეტალებს. ამოწმებს ნომერს, ჯავშნის კავშირს, თანხას, ვალუტას, `preAuth`-ს და წარმატების სტატუსს.
7. მხოლოდ გადამოწმების შემდეგ ბაზაში ფიქსირდება `paid` და იმავე ტრანზაქციაში იქმნება მფლობელის ელფოსტის გაგზავნის დავალება.
8. ფონური პროცესი აგზავნის წერილს. დროებითი შეცდომისას რიგში ინახავს და მოგვიანებით ხელახლა ცდის.

მომხმარებლის ბანკიდან დაბრუნება თავისთავად **არ ადასტურებს გადახდას**. ბანკის შეტყობინებაც გადამოწმებას იწვევს და მისი შიგთავსი სანდო გადახდის მტკიცებულებად არ გამოიყენება. დადასტურება ბრაუზერის დახურვის შემდეგაც შესაძლებელია, თუ სერვერი მუშაობს.

ეს ჩვეულებრივი ონლაინ მიღების ნაკადია: თანხის მიღებასა და მერჩანტის ანგარიშზე ანგარიშსწორებას გადახდის პროვაიდერი მართავს თქვენი ხელშეკრულების მიხედვით. სხვა პირებს შორის თანხის განაწილება, მარკეტპლეისის გადარიცხვები და ცალკე საბანკო ტრანსფერები ამ პროექტში არ არის განხორციელებული.

## 6. TBC-ის რეალური ინტეგრაციის ჩართვა

ჯერ საჭიროა TBC E-Commerce-ის მერჩანტი/ბანკის მხრიდან შესაბამისი წვდომა. ოფიციალური ინსტრუქციებით:

- `Client ID` და `Client Secret` მიიღება მერჩანტის პორტალზე: https://ecom.tbcpayments.ge/ → საიტების მართვა;
- `API Key` მიიღება TBC Developers Portal-ზე რეგისტრირებული E-commerce აპლიკაციისთვის;
- ბანკის callback უნდა მიუთითოთ მერჩანტის პორტალშიც;
- სერვერს სჭირდება ინტერნეტიდან მისაწვდომი HTTPS მისამართი. თქვენი კომპიუტერის `localhost` ბანკისთვის მისაწვდომი არ არის.

`.env`-ში დააყენეთ თქვენი რეალური მონაცემები:

```dotenv
PAYMENT_PROVIDER=tbc
TBC_PAYMENTS_ENABLED=true
TBC_API_KEY=YOUR_API_KEY
TBC_CLIENT_ID=YOUR_CLIENT_ID
TBC_CLIENT_SECRET=YOUR_CLIENT_SECRET
APP_URL=https://your-domain.ge
DB_PATH=./data/live-bookings.sqlite
HOST=0.0.0.0
PORT=3000
```

Callback-ის მისამართი იქნება:

```text
https://your-domain.ge/api/payments/tbc/callback
```

აქ მოცემული დომენი მაგალითია. ჩაწერეთ თქვენი ნამდვილი HTTPS დომენი. `APP_URL` უნდა იყოს ძირითადი მისამართი, ბოლოში დამატებითი გზის ან პარამეტრის გარეშე.

გამოიყენება API: `https://api.tbcbank.ge/v1/tpay`. კოდში არ არის გამოგონილი sandbox URL. TBC-ის დოკუმენტირებული სატესტო ეტაპი ითვალისწინებს თანხის ლიმიტს და მცირე ტრანზაქციებით შემოწმებას; **არ ჩათვალოთ ბანკთან ჩართული რეჟიმი უფასო, სიმულირებულ გადახდად**. თქვენს ტესტში შესაძლო რეალურ ჩამოჭრას წინასწარ შეათანხმებთ ბანკთან. ნიმუშის ტურების ფასები შეიძლება აღემატებოდეს თქვენი მერჩანტის სატესტო ლიმიტს.

`DB_PATH` აუცილებლად იყოს საცდელი ბაზისგან განსხვავებული. პროგრამა ერთ ბაზაში demo და TBC ჩანაწერების შერევას ბლოკავს.

ეს ვერსია იყენებს ბარათით გადახდას (`methods: [5]`), `preAuth: false` და 12-წუთიან გადახდის ბმულს. განმეორებითი გადახდა, შენახული ბარათი, განვადება და Split აქ არ არის ჩართული. TBC-ის ოფიციალური მაგალითის გადამისამართება მიიღება მხოლოდ `https://tpay.tbcbank.ge` მისამართზე; თუ ბანკი სხვა ოფიციალურ ჰოსტს მოგცემთ, გადაამოწმეთ ბანკთან და შემდეგ შეცვალეთ `CHECKOUT_HOSTS` სია.

ბანკის API პარამეტრები შეინახეთ მხოლოდ სერვერის გარემოში. `.env` არ იგზავნება ბრაუზერში და `.gitignore`-შია გამორიცხული.

## 7. მფლობელის ელფოსტაზე გაგზავნა

საჭიროა SMTP სერვისი და გამგზავნი მისამართი/დომენი, რომლის გამოყენებაც ამ სერვისში დაშვებულია. `.env`-ის მაგალითი:

```dotenv
EMAIL_TRANSPORT=smtp
OWNER_EMAIL=owner@your-domain.ge
MAIL_FROM=Tour Bookings <bookings@your-domain.ge>
SMTP_HOST=smtp.your-provider.com
SMTP_PORT=587
SMTP_SECURE=false
SMTP_USER=YOUR_SMTP_USERNAME
SMTP_PASS=YOUR_SMTP_PASSWORD
```

587 პორტზე პროგრამა STARTTLS დაშიფვრას მოითხოვს. თუ პროვაიდერი 465 პორტს იძლევა, გამოიყენეთ `SMTP_PORT=465` და `SMTP_SECURE=true`. პარამეტრების შეცვლის შემდეგ სერვერი გადატვირთეთ.

`sent` ნიშნავს, რომ SMTP სერვისმა წერილი მიიღო; ეს არ არის Inbox-ში მოხვედრის გარანტია. საჭიროა გამგზავნი დომენის სწორად დაყენება და რეალური მიმღებით შემოწმება. პროგრამა იყენებს ერთ ელფოსტის დავალებას თითო ჯავშანზე და სტაბილურ `Message-ID`-ს. SMTP-ის მიღებასა და ბაზაში ამის შენახვას შორის ავარიისას განმეორებითი გაგზავნა მაინც შესაძლებელია — აბსოლუტური „ზუსტად ერთხელ“ მიწოდება დაპირებული არ არის.

საცდელი `preview`-დან SMTP-ზე გადასვლა უკვე შექმნილ საცდელ წერილებს ავტომატურად არ აგზავნის. SMTP-ის შესამოწმებლად ახალი საცდელი ჯავშანი შექმენით მხოლოდ თქვენი მიმღები ელფოსტით.

## 8. რეალურ სერვერზე გაშვება

```bash
npm ci
npm run build
npm start
```

რეალურ გარემოში დააყენეთ `NODE_ENV=production`. ამ რეჟიმში პროგრამა მოითხოვს TBC-სა და SMTP-ს სრულ პარამეტრებს. HTTPS-ისთვის გამოიყენეთ ჰოსტინგის/რევერსული პროქსის შესაბამისი კონფიგურაცია. `TRUST_PROXY_HOPS` მიუთითეთ მხოლოდ თქვენი სერვერის რეალური სქემის მიხედვით; მაგალითად `1` მხოლოდ ერთი სანდო პროქსის შემთხვევაში.

სერვერი მუდმივად უნდა მუშაობდეს — ბანკის callback-სა და წერილის რიგს მომხმარებლის ბრაუზერი არ ასრულებს. ეს პროექტი გათვლილია **ერთ Node.js პროცესზე და დისკზე შენახულ SQLite ბაზაზე**. ჰოსტინგს უნდა ჰქონდეს მუდმივი დისკი. მხოლოდ სტატიკური ჰოსტინგი ან დროებითი ფაილური სისტემის მქონე ფუნქცია ამ კოდისთვის საკმარისი არ არის. რამდენიმე სერვერზე გაშვებისას ბაზა და სამუშაო რიგი მოარგეთ PostgreSQL-ს/საერთო რიგს.

ბაზაში ინახება მომხმარებლის საკონტაქტო მონაცემები. შეიზღუდოს ფაილის წვდომა და მოეწყოს სარეზერვო ასლები. WAL რეჟიმის აქტიური ბაზის ასლისთვის გამოიყენეთ SQLite-ის backup მექანიზმი ან ჯერ გააჩერეთ პროგრამა; მხოლოდ `.sqlite` ფაილის ცოცხლად კოპირებამ ბოლო მონაცემები შეიძლება გამოტოვოს.

## 9. ზუსტი საზღვრები და გაურკვეველი გადახდები

- ეს არის გასაშვები საწყისი ვერსია, არა ბანკის მიერ უკვე სერტიფიცირებული/გააქტიურებული საბოლოო სისტემა.
- რეალური TBC ტრანზაქცია და რეალური SMTP გაგზავნა მომზადებისას არ შესრულებულა. ტესტებში ბანკი და ელფოსტის სერვისი ჩანაცვლებულია კონტროლირებადი საცდელი პასუხებით.
- ტურის ადგილების რაოდენობა, დაკავებული კალენდარი, მინიმალური წინასწარი დაჯავშნის დრო, გასვლის საათი, გაუქმების პირობები და თანხის დაბრუნების პროცედურა ბიზნესის წესებით დასამატებელია. ამ ვერსიაში დასაშვებია დღევანდელი დღიდან 365 დღემდე ნებისმიერი კალენდარული თარიღი და 1–10 მგზავრი თითო ჯავშანზე.
- ყველა ფასი სრული გადასახდელი თანხის ნიმუშია. გადასახადის, საკომისიოს ან დამატებითი სერვისის გამოთვლის ცალკე წესი არ არის.
- თანხის დაბრუნება ავტომატურად არ კეთდება. მიღებული `Returned`, `PartialReturned` ან მოულოდნელი წინასწარი ავტორიზაცია გადადის `review` მდგომარეობაში და ორგანიზატორის შემოწმებას საჭიროებს.
- თუ გადახდის შექმნის პასუხი დაიკარგა, ჯავშანი იქნება `unknown`. პროგრამა ავტომატურად ახალ საბანკო გადახდას არ ქმნის. ავთენტიფიცირებულ callback-შემოწმებას შეუძლია აღადგინოს კავშირი ბანკის `extra2` ველით.
- უცნობი callback-ის წაკითხვის დროებითი ჩავარდნა ხელახლა მოწმდება მინიმუმ 24 საათის განმავლობაში. ცნობილ გადახდებს პროგრამა განაგრძობს ხელახლა შემოწმებას. თუ ბანკმა callback საერთოდ არ გამოგზავნა და საწყისი პასუხიც დაიკარგა, საჭიროა მერჩანტის პორტალში/ბანკთან ხელით შეჯერება ჯავშნის ID-ით. ხელახლა გადახდას მანამდე ნუ დაიწყებთ.
- მფლობელის სრული ადმინისტრირების პანელი, SMS და მომხმარებლისთვის მეორე ელფოსტა ამ მოცულობაში არ შედის.
- ჯავშნის სტატუსის გასაღები ინახება იმავე ბრაუზერის სესიაში. ბანკიდან დაბრუნდით იმავე ჩანართში/ბრაუზერში. სხვა მოწყობილობიდან სტატუსის ნახვა ამ საწყის ვერსიაში ცალკე აღდგენის პროცესს საჭიროებს.
- საწარმოო მომსახურებისთვის საჭიროა ტრანზაქციებისა და გაუგზავნელი წერილების მონიტორინგი. API-ს ლიმიტები პროცესის მეხსიერებაშია; რამდენიმე ინსტანციისას საერთო საცავი გამოიყენეთ. Callback-ზე ბანკის ოფიციალური IP-ების დაშვება შეგიძლიათ გაამყაროთ რევერსულ პროქსიში.

```bash

```

ბრძანება ამოწმებს TypeScript-ს, უშვებს ავტომატურ ტესტებს და აგებს JavaScript ვერსიას. ტესტები არ უკავშირდება რეალურ ბანკს და არ აგზავნის ნამდვილ წერილს. ისინი ამოწმებს განმეორებულ მოთხოვნებს, ფასს, საიდუმლო წვდომას, გაყალბებულ callback-ს, თანხის/ვალუტის შეუსაბამობას, წარუმატებელ გადახდას, SMTP შეცდომას, გადატვირთვის შემდეგ შენახულ რიგს და გაურკვეველი გადახდის აღდგენას.

გადამოწმების თარიღი: 2026-10-26. შედეგი: **31 ტესტი წარმატებულია**, TypeScript შემოწმება და build წარმატებულია. წარმოებაში გამოყენებული დამოკიდებულებების `npm audit --omit=dev` შემოწმებამ იმ მომენტში ცნობილი მოწყვლადობა არ აჩვენა; ეს უსაფრთხოების სრული გარანტია არ არის.

დესკტოპის ბრაუზერში შემოწმდა გვერდის დიზაინი, ფორმიდან საცდელი გადახდის გახსნა, წარმატებული შედეგი და მფლობელის წერილის შიგთავსი გამოგონილი მონაცემებით. კოდის ან დამოკიდებულებების შეცვლისას ტესტები ისევ გაუშვით. TypeScript შეცდომების ნაწილის ადრეულ აღმოჩენას ეხმარება; არც ერთი პროგრამირების ენა არ იძლევა ყველა სამომავლო ხარვეზის გამორიცხვის გარანტიას.
